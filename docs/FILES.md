# File Map

[中文](FILES.ZH.md) | English

This document answers four questions:

1. What is each file for?
2. Who generates it?
3. Which files are safe to edit by hand, and which are not?
4. What is the shortest path to add or change a capability?

> The JSON code blocks below are documentation only and use `javascript`
> highlighting; actual JSON files cannot contain comments.

Path conventions:

- `skills/...`, `profiles/...`, `toolkits/...` are relative to the `rea-toolkit`
  repository root.
- `<workspace>/...` means `.comate/reconstruction-<domain>/` inside a project.
- `<workspace>` is generated by `reconstruction-scaffold` /
  `reconstruction-bootstrap`.

## 2. The `capabilities/` directory (key)

This is the most confusing directory. It contains the **capability ledger**, the
**case mapping**, and the **per-capability dossiers** at the same time.

### 2.1 Data flow

```text
state.json#features ─────────────┐
corpus/**/case.json ─────────────┼─> build_capability_index.py
evidence/audit/*.json ───────────┘        │
                                          ├─> capabilities/index.json
                                          ├─> capabilities/case-manifest.json
                                          └─> capabilities/README.md
                                                    │
                                                    v
                                     build_feature_dossiers.py
                                                    │
                                                    v
                          capabilities/<feature-id>/README.md
                                                    │
                                                    v
                                     validate_capability_ids.py
```

In one sentence:

- `index.json` is the **capability view**: the current status of each capability.
- `case-manifest.json` is the **case view**: which capabilities each case covers.
- `capabilities/<feature-id>/README.md` is the **narrative view**: how the capability
  was reconstructed.
- `README.md` is the **catalog view**: all capabilities grouped by category.

### 2.2 `capabilities/index.json`

**Purpose**: a normalized capability table and the main machine-readable index.

Each capability roughly contains:

```javascript
{
  // Semantic capability ID
  "id": "pie3d.flat-import-inset",
  // Human-readable name
  "name": "3D pie flat-import inset",
  // Category / group
  "category": "pie",
  // Kind / object type
  "kind": "pie3D",
  // Tags / protocol fields
  "tags": ["c:pie3DChart"],
  // Completion: complete / effect-matched-source-partial / partial
  "completion": "complete",
  // Source axis
  "source": {
    // UNKNOWN / LOCATED / DECODED / EXACT / PARTIAL / NONPORTABLE
    "status": "EXACT",
    // Source evidence refs
    "refs": ["evidence/source/..."],
    // Source verdict summary
    "verdict": "...",
    // Remaining gaps / unresolved points
    "gap": null
  },
  // Effect axis
  "effect": {
    // PENDING / MATCH / DIFF / NO_REFERENCE / ACCEPTED_NONPORTABLE
    "status": "MATCH",
    // Effect evidence refs
    "refs": ["runs/.../shots/cmp.png"]
  },
  // Case refs
  "cases": {
    // Related case IDs
    "refs": ["pie/pie3d-01"],
    // Per-case verdicts
    "verdicts": {}
  }
}
```

- **Generated by**: `tools/capabilities/build_capability_index.py`
- **Inputs**: `state.json#features`, `corpus/**/case.json`,
  `evidence/audit/*.json`, the existing `case-manifest.json`
- **Safe to edit by hand?** No. Change `state.json` / `case.json` and regenerate.
- **Used for**: validation, statistics, dossier generation, quick lookup

### 2.3 `capabilities/case-manifest.json`

**Purpose**: the case → capability mapping and the case-centric index.

Each case roughly contains:

```javascript
{
  // Case ID: <group>/<case>
  "id": "pie/pie3d-01",
  // Origin: provided / derived
  "origin": "derived",
  // Kind: fixture / screenshot / trace / etc.
  "kind": "fixture",
  // Path relative to the workspace
  "path": "corpus/derived/pie/pie3d-01",
  // Capability IDs covered by this case
  "capabilities": ["pie3d.flat-import-inset"],
  // Mapping source: declared / audit / manual / unmapped
  "mapping": "declared",
  // Effect verdict
  "effect": { "status": "MATCH" },
  // Source verdict
  "source": { "status": "EXACT" }
}
```

- **Generated by**: `build_capability_index.py`
- **Sources**:
  1. `corpus/**/case.json` (recommended; explicit declaration)
  2. cases with an `id` in `evidence/audit/*.json`
  3. the previous `case-manifest.json` (manual entries take precedence)
- **Safe to edit by hand?** Yes, but new cases should preferably be declared in
  `corpus/**/case.json`; manual entries win by `id`.
- **Used for**: answering "which capabilities does this case validate?" and "which
  cases does this capability have?"

### 2.4 `capabilities/README.md`

**Purpose**: a human-readable catalog of all capabilities grouped by category,
overwritten by the generator.

- **Generated by**: `build_capability_index.py`
- **Safe to edit by hand?** No. Change `state.json` and regenerate.

### 2.5 `capabilities/_TEMPLATE/README.md`

**Purpose**: the template for a new capability dossier.

It contains:

- observed behavior
- source/protocol evidence
- case table
- implementation files
- verification / run
- gaps / next step

**How to use it**:

```bash
mkdir -p capabilities/<feature-id>
cp capabilities/_TEMPLATE/README.md capabilities/<feature-id>/README.md
```

Then:

1. add the capability to `state.json#features`;
2. declare the case in `corpus/.../case.json`;
3. run `build_capability_index.py`;
4. run `build_feature_dossiers.py`;
5. run `validate_capability_ids.py`.

### 2.6 `capabilities/<feature-id>/README.md`

**Purpose**: the dossier for a single capability and the single narrative entry
point for "how this feature was reconstructed".

Structure:

```markdown
# <capability name> (`<feature-id>`)

- Category / Kind / Tags
- Source / Effect / Completion

## 1. Observed behavior
## 2. Source/protocol evidence
## 3. Case
## 4. Implementation
## 5. Verification / run
## 6. Gaps / next step
```

The generator only maintains this block:

```markdown
<!-- GENERATED:START -->
...
<!-- GENERATED:END -->
```

- **Inside the block**: updated by `build_feature_dossiers.py`; do not edit by hand.
- **Outside the block**: manual notes; the generator does not overwrite them.

This is the key file that lets a different model understand how the capability was
reconstructed.

### 2.7 `feature-id` vs `case-id`

| | feature-id | case-id |
|---|---|---|
| Answers | which observable behavior/rule was reconstructed | which input validates it |
| Example | `pie3d.flat-import-inset` | `pie/pie3d-01` |
| Stored in | `state.json#features`, `index.json`, dossier directory | `corpus/**/case.json`, `case-manifest.json` |
| Relationship | one capability can have many cases | one case can cover many capabilities |

## 3. Workspace root

| File | Purpose | Generated by | Safe to edit by hand? |
|---|---|---|---|
| `PIPELINE.md` | 6-stage process, directory contract, hard rules | scaffold/bootstrap | Only when changing the process |
| `README.md` | Workspace map and shortest onboarding path | scaffold/bootstrap | Can be extended |
| `state.json` | Capability state machine: features/backlog/queue/runScope | Humans + tools | **Yes; source of truth** |
| `domain.md` | Human-readable domain config | scaffold | Yes; add reference/target/acceptance |
| `profile.json` | Machine-readable domain config | scaffold (JSON profile) | Yes; tool checks read it |
| `bootstrap.json` | Initialization record (profile, tool checks, ledger counts) | bootstrap | Do not edit by hand |

### `state.json`

The most important fields:

```javascript
{
  // Full capability ledger
  "features": [
    {
      // Semantic capability ID
      "key": "domain.feature",
      // Human-readable name
      "featureName": "...",
      // Category / group
      "category": "...",
      // Source axis
      "sourceStatus": "UNKNOWN",
      // Effect axis
      "effectStatus": "PENDING",
      // Source evidence refs
      "sourceRefs": [],
      // Effect evidence refs
      "effectImageRefs": [],
      // Related case IDs
      "caseRefs": []
    }
  ],
  // Candidate capabilities / gaps
  "backlog": [],
  // Pending capability queue
  "queue": [],
  // Scope selected for the current task batch
  "runScope": { "features": [], "requiredCases": [], "requiredRegressions": [] }
}
```

- `key` must be a semantic ID (`<domain>.<feature>`); do not use batch numbers such
  as `ext-47`.
- `sourceStatus` / `effectStatus` are independent axes and cannot replace each other.
- `runScope` is the work order for the current task batch, not the full table; the
  full table is `features` / `capabilities/index.json`.
- `queue` is the prioritized pending queue; `selectedFeature` is the single capability
  currently being worked on.
- `index.json` is generated from this file. **Do not edit index by hand and expect
  state to update in reverse.**

## 4. `corpus/`

| Path | Purpose |
|---|---|
| `corpus/provided/` | Real inputs from users/upstream; covers real usage scenarios; no minimality requirement |
| `corpus/derived/` | **Minimal attributable cases** derived from source/protocol evidence |
| `corpus/**/case.json` | Per-case capability mapping declaration |
| `corpus/**/reference/` | Reference outputs (screenshots/logs/frames) |
| `<group>/<case>/` | A case group directory; stable, searchable names |

Minimal `case.json` shape:

```javascript
{
  // Case ID: <group>/<case>
  "id": "<group>/<case>",
  // Origin: provided / derived
  "origin": "provided|derived",
  // Kind: fixture / screenshot / trace / etc.
  "kind": "fixture",
  // Capability IDs covered by this case
  "capabilities": ["<domain>.<feature>"],
  // Effect verdict
  "effect": { "status": "PENDING" },
  // Source verdict
  "source": { "status": "PENDING" }
}
```

## 5. `evidence/`

| Path | Purpose |
|---|---|
| `evidence/source/` | Static decompilation/protocol conclusions: functions, addresses, formulas, defaults, boundaries |
| `evidence/source/raw/<date>/` | Raw decompilation dumps/crops, frozen, with `MANIFEST.md` |
| `evidence/runtime/` | Runtime probes, hooks, traces, logs |
| `evidence/runtime/raw/<date>/` | Session-level raw logs, frozen, with `MANIFEST.md` |
| `evidence/audit/` | Per-case source/effect verdict JSON (optional) |

Naming:

```text
evidence/source/<feature-id>-<YYYY-MM-DD>.md
evidence/runtime/<feature-id>-<YYYY-MM-DD>.jsonl
```

Rules: feature-id is the primary key; dates are only for provenance; raw dumps go in
`raw/`, and conclusions do not.

## 6. `runs/`

| Path | Purpose | Lifecycle |
|---|---|---|
| `runs/_TEMPLATE/` | Template for a new run | read-only |
| `runs/_TEMPLATE/run.json` | Run metadata template | read-only |
| `runs/regress-baseline/` | Current regression baseline | updated only by the baseline refresh flow |
| `runs/regress-current/` | Latest regression's disposable output | safe to overwrite |
| `runs/archive/` | Frozen historical runs/regressions | read-only |
| `runs/<run-id>/` | Formal record of one experiment/regression | write new work here |

`run-id`:

```text
YYYY-MM-DD-<feature-id>-NN
```

`run.json` records the command, feature, case list, baseline, result, and notes;
`result.json` records per-case metrics/verdicts.

## 7. `tools/capabilities/`

| Script | Purpose | Input | Output |
|---|---|---|---|
| `build_capability_index.py` | Generate the capability ledger | `state.json`, `corpus/**/case.json`, `evidence/audit/*.json`, previous manifest | `index.json`, `case-manifest.json`, `README.md` |
| `build_feature_dossiers.py` | Generate/refresh per-capability dossiers | `index.json`, `case-manifest.json` | `capabilities/<feature-id>/README.md` |
| `show_capability.py` | Compact view of one capability | `index.json`, `case-manifest.json` | terminal summary |
| `validate_capability_ids.py` | Validate IDs/status/cases/dossiers | `index.json`, `case-manifest.json`, `state.json`, `profile.json` | error list / `OK` |

Recommended order:

```bash
python3 tools/capabilities/build_capability_index.py
python3 tools/capabilities/build_feature_dossiers.py
python3 tools/capabilities/validate_capability_ids.py
```

`tools/INDEX.md` is the index of project-specific tools; update it when adding a
tool.

## 13. Files that should not be edited by hand

| File | Reason |
|---|---|
| `capabilities/index.json` | Overwritten by `build_capability_index.py` |
| `capabilities/case-manifest.json` | Re-merged; add new cases via `corpus/**/case.json` |
| `capabilities/README.md` | Overwritten by the generator |

| `bootstrap.json` | Generated by bootstrap |
| `runs/regress-baseline/` | Updated only by the baseline refresh flow |
| `history/` | Frozen archive |

## 14. Files that are safe to edit

- `state.json#features` / `backlog` / `queue`
- `corpus/**/case.json`
- Outside the `GENERATED` block in `capabilities/<feature-id>/README.md`
- `domain.md` / `profile.json`
- `PIPELINE.md` (only when changing the process)
- Project-specific `tools/` and `tools/INDEX.md`

## 15. Shortest paths

### Add a capability

```text
1. Add a key to state.json#features
2. cp capabilities/_TEMPLATE/README.md capabilities/<feature-id>/README.md
3. Declare capabilities in corpus/derived/<group>/<case>/case.json
4. python3 tools/capabilities/build_capability_index.py
5. python3 tools/capabilities/build_feature_dossiers.py
6. python3 tools/capabilities/validate_capability_ids.py
```

### Add a case

```text
1. Put the input in corpus/derived/<group>/<case>/
2. Write case.json and declare capabilities
3. Run build_capability_index.py
4. Add reference/target outputs to the dossier's Case table
```

### Change a capability verdict

```text
1. Change sourceStatus/effectStatus/refs in state.json#features
2. Edit notes outside the dossier's GENERATED block
3. Rebuild + validate
```

### Add a platform

```text
1. Copy profiles/_TEMPLATE.json
2. Fill platform/source_roots/reference_runtime/target_runtime/comparison/toolchains
3. npx /path/to/rea-toolkit doctor --profile <name>
4. Use bootstrap to generate a temporary workspace and verify it
```
